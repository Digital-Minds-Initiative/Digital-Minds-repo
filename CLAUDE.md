# CLAUDE.md

Guidance for Claude Code (and other AI assistants) working in this repository. Read it fully before changing code. The human-facing versions are `README.md` and `docs/architecture.md`; decisions are in `docs/adr/`.

## Project

Digital Minds — platform for the tech student clubs at Umm Al-Qura University. UI is **Arabic, RTL-first**. Phase one: members & points (clubs, committees, membership types, hierarchical permissions, a points ledger). People sign in with a one-time code emailed to their university address (ADR 0014). One Next.js 16 app (App Router, Route Handlers as the backend), TypeScript strict, PostgreSQL + Prisma 7, Zod 4, Tailwind 4, next-intl, TanStack Query + Table v9, React Hook Form, MSW 3, Vitest 5, Storybook 10, pnpm 12, Node 24.

## Commands

```bash
pnpm dev                    # app on :3000 (DB via `docker compose up -d`)
pnpm typecheck              # next typegen + tsc
pnpm lint                   # ESLint incl. architecture boundaries (slow-ish: type-aware)
pnpm knip                   # unused files, exports, dependencies (CI runs it; config: knip.jsonc)
pnpm test                   # unit tests (no DB)
pnpm test:integration       # needs Docker DB; uses digital_minds_test (auto-created, wiped)
pnpm test:e2e               # Playwright, real app on :3100 + digital_minds_e2e_test (reseeded); PLAYWRIGHT_CHANNEL=msedge to use Edge
pnpm build                  # production build
pnpm storybook              # :6006
pnpm db:migrate --name x    # after editing prisma/schema.prisma (--create-only first if you will hand-edit the SQL)
pnpm db:seed                # replaces local data with the demo dataset
```

Run `pnpm typecheck && pnpm lint && pnpm test` before declaring work done; add `pnpm test:integration` when server code changed.

Never run `prisma migrate reset`, `pnpm db:reset`, `pnpm db:seed` or anything that drops data without the user's explicit consent in the current conversation.

## Architecture rules (enforced by ESLint where possible — do not disable them)

1. **Three trees** (ADR 0013): backend in `src/server/` (modules in `src/server/modules/<module>/`: service, repository, policies, mappers, `index.ts`), frontend in `src/client/` (`features/<module>/` with components, hooks, messages, mocks, `index.ts`; plus `lib/` and `mocks/`), and `src/shared/` (`contracts/<module>.ts` + `contracts/core/`, `lib/`, `demo/`). Pages in `src/app/[locale]`, route handlers in `src/app/api/v1`; the design system stays in `src/components`. Outside code uses a server module only through its `index.ts`, a client feature only through `index.ts`, `mocks/index.ts` or `messages/`. Never deep-import another module's files.
2. **Client never imports server, server never imports client** (`src/client`, `src/components`, pages ↔ `src/server`, route handlers); both may import `src/shared`, which imports neither. Every server file starts with `import 'server-only';`.
3. **Pages and layouts (`src/app/[locale]`) never call services.** UI data goes through `/api/v1` with TanStack Query hooks built on `apiClient` (`src/client/lib/api-client.ts`). No Server Actions.
4. **Route handlers are one line** (the one exception is `health`, which maps a degraded check to 503): `export const GET = defineRoute(endpoint, ({ actor, query }) => service(actor, query));` No logic, no Prisma, no authz calls. Sign-in endpoints pass `client` (IP, session token) and wrap the result in `withSession` to set the cookie: `verifyOtp(body, client).then(withSession)`.
5. **Services take the `Actor` as the first argument**, read through scopes, assert roles, then write through scoped repository functions:
   - outside scope → `NotFoundError` (404);
   - visible but the role may not act → `AuthzError` (403, from `src/server/authz`);
   - conflicting state → `ConflictError(message, reason)` (409); unique-constraint violations already become 409 `already_exists` in the db client — don't catch P2002 in repositories;
   - business validation → `ValidationError` (422);
   - too many requests → `RateLimitedError(reason, retryAfterSeconds)` (429).
6. **Only repositories use Prisma** (`src/server/modules/*/repository.ts`, plus `src/server/authz/actor-repository.ts`). Repository functions for scoped models take a branded scope (`MemberScope`, `PointTransactionScope`…) and combine it as `AND: [scope, filters]` — including writes: updates use `updateMany` with the scope, creates first check their parent rows through the scope in the same transaction. Prove it in `tests/integration/repositories/` (call the write with another club's scope; assert nothing changed). Never build a scope by hand or cast to a scope type. `$queryRaw` is allowed in a repository for **row locking** (`SELECT … FOR UPDATE`, inside a transaction, always parameterised — see `lockMembershipTypes` and ADR 0016) and for the one upsert Prisma cannot express, the rate-limit counter (`INSERT … ON CONFLICT DO UPDATE … RETURNING` in `modules/rate-limit/repository.ts`, which has to be a single statement to be safe). Everything else reads and writes through the model API.
7. **Contracts first.** Every endpoint is a `defineEndpoint({...})` in `src/shared/contracts/<module>.ts` (Zod for params/query/body/response). Contracts import only `zod`, `@/shared/contracts/core`, other contracts and `@/shared/lib` — never Prisma or React. Response schemas are the whitelist of what leaves the server.
8. **Authorization changes need integration tests** in `tests/integration/` proving both the error and that the database did not change. Use `tests/factories/scenario.ts`.

## Authorization model (summary — details in docs/architecture.md and ADR 0002)

- Full admin (`User.isFullAdmin`) → everything. Club officer (`Membership.role = CLUB_OFFICER`) → everything in that club. Committee lead (`CommitteeMembership.role = LEAD`) → reads that committee's members, runs their points, and may change a member's membership type — nothing else on a membership (ADR 0017). Adding, removing, committee assignment and every profile field stay with officers and full admins, with one reason, `club_management_required`. Membership types never grant anything.
- The Actor contains only _active_ memberships; removed rows grant nothing. Removing a member resets roles, and restoring a membership or a committee membership resets them again — coming back never restores officer or lead rights.
- **Members** (ADR 0017): adding matches a person by university email (one account per person); a removed membership is **restored** with its id, so its committee memberships and their points come back, while someone already active in the club is 409 `already_in_club` with their `memberId` in `error.details`. PATCH bodies are strict — an unknown field is 422, a field the actor may not change is 403, nothing is silently dropped. The university email is an officer's to correct only before the person registers; afterwards a full admin may move the account. Either way the change ends every session that person holds, in the same transaction. A field whose submitted value already equals the stored one (compared after normalising) is not an edit: it is neither permission-checked nor written.
- **CSV import** (ADR 0021): the same rule as adding one member (officers and full admins, club from the URL, 409 `club_archived`), as two steps over one body — `POST /clubs/:clubId/members/import/preview` classifies every row (`add`, `restore`, `existing`, `invalid`) and writes nothing; `POST /clubs/:clubId/members/import` takes the same file with the preview's `checksum`, rebuilds the plan inside the transaction that writes and refuses with 409 `import_changed` if it differs. `add` deliberately covers both a new address and an account that exists in another club, and the file's name never overwrites a stored one — `name_differs` is a warning on `existing`/`restore` rows only, never on `add` (ADR 0012). The file is base64 in the JSON body (so the CSRF rule holds and the server sees the bytes): refuse what is not UTF-8 text with 422 `unsupported_encoding`, sniff the delimiter, 1 MB and 1000 rows. `GET …/import/template` answers with `withFile`.
- **Members export** (ADR 0025): `POST /clubs/:clubId/members/export` with `{ columns, filters, selection }` — `filters` is the list's own filter shape (`memberListFiltersShape`) and the rows come from the list's own `resolveListFilters` + `findListedMembers`, so never write a second copy of the list's rules for it. Same scope as the list; an actor who can list nobody in the club gets 404. Ticked ids must all be in the filtered list or nothing is exported (422 `entries_rejected`, `not_found` per id); 5000 rows (422 `too_many_rows`, counted first); 30 per person per hour. The file is `write-excel-file`, built in memory: header alone in row 1 (re-importable as CSV), text cells typed as text, every text cell starting with `= + - @`, tab or CR prefixed with `'` (`neutraliseFormula` — never write a `Formula` cell), Saudi phones as `05…`, an about sheet with the points basis. Each file writes one `MemberExport` row (filters without the search text, never the data), after the file is built.
- **Roles** (ADR 0018): full admins appoint and revoke club officers (403 `full_admin_required`); a club's officers appoint and revoke the leads of its committees (403 `club_management_required`); a lead appoints nobody and sees no role history. The full-admin flag is not grantable through the API. A committee may have several leads, an officer may appoint themselves, and there is deliberately no self-role rule — nothing could reach it. Granting a role someone already holds writes nothing and answers 200: the role write is `updateMany` conditioned on the previous role, and the append-only `RoleChange` row is inserted only when that changed something, so two simultaneous grants leave one row. Role history records explicit grants and revokes only — a role cleared by a removal shows as `removedAt`, not as a row.
- **Points** (ADR 0004, amended by ADR 0019): a lead runs the ledger of the committees they lead, including transactions somebody else recorded (403 `points_management_required`, which no request can actually reach — the scopes already imply it, so it is unit-tested). Amounts are whole numbers in ±1000, never zero; a reason is required and goes through `collapseWhitespace`; a work date is a Riyadh calendar date, never in the future. Refusals name what is wrong — 409 `member_removed`, `not_in_committee`, `club_archived`, `committee_archived` — and 404 stays for what the actor cannot see. Cancelling is final and idempotent, and the conditional update inside the transaction decides it: nothing matched + row now CANCELLED → the 200 no-op, still ACTIVE → 409 `transaction_modified`, unreachable → 404. An edit whose values already match writes nothing.
- **The members list** (ADR 0020): filters are club, one `committeeId`, one or more `membershipTypeId`, a work-date period (`from`/`to`), `q` and `status`. Each is resolved through its own scope first — outside it is a 404, a different club than the request implies is a 422 — so a filter can only narrow what the actor sees. The period decides which points count, never which members are listed, and `pointsBasis` on the response names the figure the column shows. Names sort on the Arabic-folded `User.searchName` (never a `COLLATE` clause, never `localeCompare`); `sort=points` is ranked by `rankByPoints` over every matching member, because the `where` is a branded scope that must not be rewritten as SQL. `sort`/`order` are optional: a period makes the default points descending.
- **Bulk points** (ADR 0022): `POST /committees/:committeeId/points/bulk` (member ids + the committee from the URL; its lead, officers, full admins) and `POST /clubs/:clubId/points/bulk` (`{ memberId, committeeId }` pairs; officers and full admins only, 403 `club_management_required` — the first points 403 a request can actually reach). One service, two thin entry points. Limits are exported contract constants (500 and 5000). Same amount/reason/workDate validation as the single add; the URL's archived club or committee refuses the lot. **All or nothing**: one unusable entry answers 422 `entries_rejected` with one issue per rejected entry (`body.memberIds[3]` / `body.entries[3].committeeId`, capped at 1000) and writes nothing. Codes: `not_found` (nonexistent **or** out of scope — the one place a scope miss is a listed entry, not a request 404), `member_removed`, `not_in_committee`, `committee_not_in_club`, `committee_archived`. Entries are judged inside the transaction that writes them. Each member gets their own `PointTransaction`; the shared `PointBatch` is display only — no bulk edit, no bulk cancel. The client sends `batchId`: the `PointBatch` primary key is the uniqueness, inserted first with `skipDuplicates`, so a resend replays (200, same body) and a concurrent duplicate waits; the same key with a different request is 409 `batch_mismatch`, and a refused request frees its key again.
- **The committee view link** (ADR 0023): every committee can have one view-only link, managed by its lead, the club's officers and full admins — `GET` / `POST` (create or renew in one step) / `DELETE` on `/committees/:committeeId/view-link`, with 403 `committee_management_required` (unreachable, unit-tested) and 409 `club_archived` / `committee_archived` on the writes while reading stays open. The token is 192 random bits; the row keeps an HMAC of it (the lookup key, keyed by `VIEW_LINK_SECRET`, which defaults to `AUTH_SECRET`) and an AES-256-GCM copy under the same secret (so it can be copied again), never the token itself. **The public view** under `/api/v1/public/committee-views/:token` (`access: 'public'`, GET only, no actor ever) is scoped by the token alone: it resolves to a committee id, and `committeeViewMembersScope` / `committeeViewPointsScope` turn that into the usual branded scopes. Response schemas are a whitelist — names, balances, and each transaction's amount, reason and work date; never contact data, membership types, other committees, cancelled transactions or any id an authenticated endpoint accepts. Unknown, renewed, turned-off and archived tokens answer one identical 404, built in one place, with the limits counted before the lookup. `defineRoute` adds `referrer-policy: no-referrer` and `x-robots-tag: noindex` to every answer of a public endpoint.
- **Rate limits** live in `src/server/modules/rate-limit` (it owns `RateLimitCounter`): `consumeFixedWindow({ name, max, windowSeconds }, subject, now)`. Each surface keeps its own numbers and its own refusal — sign-in in `auth/rate-limits.ts`, the public view in `clubs/view-rate-limits.ts` (60/minute and 600/hour per IP, 1200/hour per token). The limit name is part of the key, so no surface spends another's budget. Its `$queryRaw` upsert is the one place raw SQL is used for something other than row locking.
- A module may read any table but writes only the tables it owns; a cross-module write inside one transaction goes through the owning module's function that takes the transaction client (`endUserSessions` in the auth module, `setClubRole` / `setCommitteeRole` in the members module).
- Clubs and committees are created, renamed, archived and restored by **full admins only**; a club's **membership types** by that club's officers and full admins. Reading clubs, committees and types is scope-only (a lead sees their club, its types and the committees they lead).
- **Archived clubs and committees** (ADR 0015) are never deleted: they drop out of lists unless `?includeArchived=true`, and accept nothing new — members, committee memberships, points, committees, membership types — each refused by the module that owns the write (409 `club_archived` / `committee_archived`). Membership types are deleted instead of archived, under the rules in ADR 0016.
- Scope builders and role predicates: `src/server/authz/{scopes,roles}.ts`. Module rules, and the `reason` each 403 carries: `src/server/modules/*/policies.ts`, written with the service that calls them (ADR 0011).
- Nested data must be scoped too (e.g. a member's committee list for a lead shows only the lead's committee).
- **Sign-in** (ADR 0014, `src/server/modules/auth/sign-in.ts`): email → 6-digit code → session cookie → name step. Nothing may reveal whether an address has an account before its code is verified (the request step never reads `User`; verify refuses wrong/expired/used/locked codes before reading it), and no `User` is created for an unverified address. Codes are HMACs keyed by `AUTH_SECRET`, 10 min, single use, 5 attempts; limits per email and per IP live in `rate-limits.ts`. `registeredAt` is set at the name step, which for an admin-added person only **confirms** the stored name (a different one is 422 `name_mismatch`; renaming is an officer's job — ADR 0017).
- `resolveActor` (`src/server/actor.ts`): a live session cookie decides alone (an incomplete session grants nothing → 401). Only without one, the dev actor switcher (`dm-dev-actor` cookie / `X-Dev-Actor` header with a university email) runs — only in development with `DEV_ACTOR_SWITCHER=true`. Never weaken its guards.
- **CSRF**: `defineRoute` refuses non-GET requests whose `Origin` is not `APP_ORIGIN` and bodies not sent as `application/json`. Tests that POST must send both (see `@tests/utils/auth`).
- **Security headers** (ADR 0024): the baseline, the `/api` policy and HSTS (production only) are in `next.config.ts`; the pages' Content-Security-Policy is built per request in `src/proxy.ts` because it carries a nonce (`buildContentSecurityPolicy` in `src/shared/lib/security-headers.ts`, which the proxy may import — `src/proxy.ts` counts as client code for the ESLint boundaries and cannot import `src/server`). A new third-party origin means editing that policy. `style-src` keeps `unsafe-inline` on purpose: the design system sets `style` attributes.

## Data model

`prisma/schema.prisma`. Names that must be unique among their siblings (club, committee in a club, membership type in a club) go through `normalizeEntityName` (`src/shared/lib/names.ts`) — in the contract field and again in the service — before they are compared or stored. UUIDv7 ids; composite foreign keys keep `clubId` consistent from `Membership` down to `PointTransaction` — when creating rows, copy `clubId`/`committeeId` from the loaded parent. All FKs are `Restrict`; nothing with history is hard-deleted (soft delete with `removedAt`, archive with `archivedAt`). `PointBatch` holds one bulk request, with the client's `batchId` as its primary key and a SHA-256 of the request; `PointTransaction.batchId` is a composite FK onto it, so a batch cannot span clubs. Points: never delete; cancel = status CANCELLED + revision; every edit writes a `PointTransactionRevision` with previous values in the same transaction, and both writes are conditional on the row being unchanged since it was read (ADR 0019). `Committee` carries its view link as three columns that are all set or all null (a CHECK constraint): `viewTokenHash` (unique), `viewTokenCipher` and `viewTokenCreatedAt` — rotating `VIEW_LINK_SECRET` invalidates every link, and a link that cannot be decrypted is reported as no link. `workDate` is a calendar date in Asia/Riyadh (`src/shared/lib/dates.ts`), never in the future. Write `User.searchName = normalizeForSearch(fullName)` whenever `fullName` is written. `User` holds only the shared identity (name, university email); contact and study details (phone, personal email, college, major, level) are per club on `Membership`, and nothing reads another club's copy (ADR 0012). Hand-written CHECK constraints live in the migrations (appended by hand after the generated SQL). Write one with `pnpm prisma migrate dev --create-only --name x`, append the constraints, **then** apply it with `pnpm db:migrate`: a migration applied before it is edited leaves that database recording the hash of the unedited file, and `migrate dev` then refuses to run against it until the row is repaired or the database is reset. Only the authoring machine is affected — a clone applies the committed file — but it is the machine you are working on. The sign-in tables (`OtpChallenge`, `Session`, `RateLimitCounter`) are short-lived and are deleted when they expire.

## Frontend rules

- **No hard-coded UI strings.** Add keys to `src/client/features/<module>/messages/ar.json` (or `src/i18n/messages/ar/*.json` for shared ones; register new namespaces in `src/i18n/messages.ts`) and use `useTranslations` / `getTranslations`. Keys are type-checked. Validation messages in contracts are keys (`date_in_future`) translated under `common.validation`.
- **RTL / logical properties only:** `ms-`/`me-`/`ps-`/`pe-`/`start-`/`end-`/`border-s`/`rounded-e`/`text-start`. Wrap arrows/chevrons in `DirectionalIcon`. Wrap emails/phones in `<bdi dir="ltr">`.
- **Design tokens:** semantic utilities only (`bg-surface-1`, `text-fg-muted`, `bg-primary`, `text-danger`, `border-border`…). No hex/rgb/oklch values, no `--palette-*` in components; Tailwind's default palette does not exist. New tokens go in `src/styles/tokens.css` (primitive → semantic) with a dark override.
- **Components:** primitives in `src/components/ui` (Radix + `cva` + `cn`), patterns in `src/components/patterns`, layouts in `src/components/shell`. Add a Storybook story for every new primitive/pattern. Use `next-intl` navigation (`@/i18n/navigation`), not `next/link`.
- **Tables:** use `DataTable` in server-side mode; sorting is opt-in per column (`enableSorting: true`) and must match the API's sort fields. Keep list state in the URL by parsing it with the contract schema (see `useMembersQueryState`).
- **Forms:** React Hook Form + `zodResolver(<contract schema>)` + `FormField`.

## Testing

- Unit tests in a `__tests__/` folder next to the code they test (`src/components` keeps its two tests colocated); component tests start with `// @vitest-environment jsdom` and use `renderWithProviders` from `@tests/utils/render`.
- CSV fixtures for the import live in `tests/fixtures/members-import/` and are read as bytes with `@tests/utils/import-file`; `.gitattributes` exempts them from line-ending normalisation, so do not "fix" their CRLF or encoding.
- Integration tests in `tests/integration/` run services/route handlers against a real DB. Each file starts from an empty DB (`beforeAll` truncate) and builds its own scenario. `tests/integration/repositories/` may import repositories directly (an ESLint exception) to test the write scopes.
- `server-only` is aliased to an empty module in Vitest.
- `@tests/utils/xlsx` opens an exported workbook (values via `read-excel-file`, sheet XML via `fflate`) and turns a sheet into the CSV Excel would save.
- `tests/integration/auth/` drives the sign-in endpoints like a browser with `@tests/utils/auth` (`signIn`, `lastCodeFor` reads the code from the dev email sender). Services that depend on time take `new Date()` and pass it to the database (no `now()` in SQL), so tests move the clock with `vi.useFakeTimers({ toFake: ['Date'] })`.
- `tests/repo/` holds checks on repository config (run with `pnpm test`).

## Gotchas specific to this stack

- **Prisma 7:** the datasource URL lives in `prisma.config.ts`; `.env` is loaded there with `@next/env` (default import — it is CommonJS). The client is generated to `src/server/db/generated` (gitignored; regenerated on install). Import types from `@/server/db/generated/client` only in repositories/authz. `migrate reset` does not seed — `pnpm db:reset` chains `db seed`.
- **`AGENTS.md` is managed by `next dev`** (it writes and restores a Next.js block there). Keep it committed; don't delete it. Version-matched Next.js docs live in `node_modules/next/dist/docs/` — read them before using an unfamiliar Next.js API.
- **Next.js 16:** middleware is `src/proxy.ts`; `params` are Promises; use `LayoutProps<'/[locale]'>` / `PageProps<'/…'>` types; `pnpm typecheck` runs `next typegen` first. Node-only startup code goes in `src/instrumentation-node.ts` (imported only when `NEXT_RUNTIME === 'nodejs'`).
- **MSW 3:** `msw/browser` cannot be bundled for the server — it is loaded through `next/dynamic` with `ssr: false` in `src/client/mocks/mock-gate.tsx`; `worker.start()` must be idempotent (React Strict Mode).
- **TanStack Table v9:** features are registered via `tableFeatures` in `components/patterns/data-table/features.ts`; build columns with `createDataTableColumnHelper<T>()`.
- **Generic helpers** (`defineRoute`, `mockEndpoint`) use `NoInfer` so the endpoint alone decides types.
- **ESLint on Windows:** `import/no-restricted-paths` globs must not start a segment with `*` (wrap new zones with the `glob()` helper in `eslint.config.mjs`).
- **Email:** without `RESEND_API_KEY` the dev sender prints emails (with the sign-in code) to the `pnpm dev` console and keeps them in memory for tests; integration tests always use it. Email HTML uses inline styles and literal colours (email clients ignore CSS variables); its strings are in `src/i18n/messages/ar/email.json`.
- **Node version:** set only in `.nvmrc` (fnm and CI read it). To change it, also update `engines` in `package.json` and the README Prerequisites; `tests/repo/toolchain-versions.test.ts` fails until all three match.
- **pnpm 12:** settings live in `pnpm-workspace.yaml`; new packages younger than one day are refused; dependencies with install scripts must be added to `allowBuilds` deliberately.
- **TypeScript 6** (not 7) and **ESLint 9** (not 10) on purpose — see ADR 0010.

## Workflow

- Branch `feat/<clickup-task-id>-short-name` (or `fix/`, `chore/`), Conventional Commits (`feat(members): …`), PR to `main` with the template, squash merge. Do not commit or push unless asked.
- Checks by task size:
  - Small, contained changes (one component, copy, styles, a single helper): run typecheck, lint and only the tests for the files you changed. Don't run the full suite or the build locally; CI runs everything on the PR.
  - Larger changes, anything touching auth, permissions, the database schema, shared contracts or more than one module: run the full suite and the build locally before opening the PR.
- Never commit `.env*` files (only `.env.example`). Never log personal data (phones, emails); log ids.
- Keep docs in sync: new env vars → `.env.example` + `src/server/env.ts`; new decisions → an ADR; changed personas → README "Seeded accounts".
